# Part II: Software

This marks the beginning of Part II: software.

In Part I, we built the complete hardware platform of a computer system, starting from NAND gates and ending with an assembler that translates symbolic assembly code into machine language. However, this alone is not enough to explain how high-level programming languages, one that can build complex and expressive programs, can ultimately run on a computer and connect to the hardware.

The central question of Part II is therefore: **how do we get from a high-level programming language to machine language?**

The mindset you currently might have is:

```
High-level language (Jack)
↓ compiler

Hack assembly
↓ assembler

Hack machine code
```

But, rather than compiling high-level code directly into machine instructions, many systems introduce an intermediate layer, called a virtual machine (vm), and the process turns into this:

```
High-level language (Jack)
↓ compiler (pass 1 to vm)

VM code
↓ compiler (pass 2 to assemlby)

Hack assembly
↓ assembler

Hack machine code
```

We call the first approach a **single-tier compilation pipeline**, and the second approach a **two-tier compilation pipeline**.

Ok, but why introduce a new intermediate layer? As we know, hardware differs from computer to computer, directly translating from high level language to assembly would mean writing a separate compiler backend for every different computer architecture.

This was very annoying back in the days for all the developers.

- If the programming language developer updated their language, they had to update all its compilers.
- If a hardware developer created new hardware, they had to hope that major programming language developers would write a compiler for their architecture.
- If a software developer wanted to launch his software on multiple different platforms, it's very likely they'll encounter portability problems, where the same source code behaved differently across machines.

So historically, that's why Java has been developed, with the slogan of:

> [Write once, run anywhere.](https://en.wikipedia.org/wiki/Write_once,_run_anywhere)

The idea was simple, create a new intermediate layer called a virtual machine, which simplified things for everyone.

![[The Elements of Computing Systems, Building a Modern Computer from First Principles 2 ed 43.jpg|500]]

[[The Elements of Computing Systems Building a Modern Computer from First Principles.pdf#page=178&rect=114,386,498,738|The Elements of Computing Systems, Building a Modern Computer from First Principles 2 ed, p.178]]

- Programming language developers only needed to write and maintain one Prog-to-VM compiler.
- Hardware developers could support new hardware themselves by implementing a VM-to-assembly translator for their architecture.
- Software developers encountered portability problems a lot lesser.

So, all of part 2 is about creating software for turning any high-level program into executable code, a high level language must go through the 1st compilation to byte code, which then goes through the 2nd compilation to assembly, which then goes through the assembler to turn into machine code, which is loaded onto the hardware.

## Stack Machine

But... what would such a VM look like? It needs to be lower leveled compared to a high level programming language, but not as low as assembly language as it's not tied to the hardware.

> [!PDF|yellow] [[The Elements of Computing Systems Building a Modern Computer from First Principles.pdf#page=179&selection=14,60,53,56&color=yellow|The Elements of Computing Systems, Building a Modern Computer from First Principles 2 ed, p.179]]
> > Thus, the desired VM language should satisfy several requirements coming both from above and from below. First, the language should have a reasonable expressive power. We achieve this by designing a VM language that features arithmetic-logical commands, push/pop commands, branching commands, and function commands. These VM commands should be sufficiently “high” so that the VM code generated by the compiler will be reasonably elegant and well structured. At the same time, the VM commands should be sufficiently “low” so that the machine code generated from them by VM translators will be tight and efficient.

Following that spirit came 2 types of VMs, stack based VMs and register based VMs.

## But What Are We Making?

Right now, we want to try to make a VM that can receive byte code and turn it into assembly language, and we will be only implementing push/pop, arithmetic/logic in this chapter.

We will look through an example.

So, say the Jack Program conceptually does this:

```
(2 + 3) - 1
```

The byte code for the stack would look like:

```
push constant 2
push constant 3
add
```

The hack assembly for this should look like:

```
// push constant 2
@2
D=A
@SP
A=M
M=D
@SP
M=M+1

// push constant 3
@3
D=A
@SP
A=M
M=D
@SP
M=M+1

// add
@SP
AM=M-1
D=M
A=A-1
M=M+D
```

It is a bit lengthy!

The book specified the design of the VM translator, which should be broken down into 2 parts:

- Parser
- CodeWriter

The Parser should:

- read `.vm` files
- break each line into command type + arguments
- ignore whitespace and comments

![[The Elements of Computing Systems, Building a Modern Computer from First Principles 2 ed 51.jpg|500]]

[[The Elements of Computing Systems Building a Modern Computer from First Principles.pdf#page=196&rect=57,276,558,733|The Elements of Computing Systems, Building a Modern Computer from First Principles 2 ed, p.196]]

The CodeWriter should:

- Know how each VM command maps to Hack assembly
- Create assembly code templates, and output `.asm` files
